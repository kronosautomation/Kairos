# Review: task leases and fencing (commit ac4e609)

Scope: `PostgresKairosStore` (workflow/activity poll, complete, release), `0001_init.sql`, `WorkerRuntime`,
`StoreContractTests`. Checked against invariants I1, I3, I8, I9 in docs/TEST-STRATEGY.md.

## What is solid
- Fencing tokens are monotonic and never reset (`runs.wf_lease_token`, `activity_tasks.lease_token`).
- Workflow completion is one guarded statement: token + head seq + head hash + state + leased, all or nothing.
- Activity completion locks run then task (consistent order, no deadlock with workflow completion) and re-checks token under lock.
- Claims use `FOR UPDATE SKIP LOCKED`; stale holders get `StaleLease`, history moved gets `SequenceConflict` + release.
- Contract tests cover reclaim-after-expiry and stale completion for both task kinds.

## Findings (most severe first)

### L1 High: no lease renewal (heartbeat) for activities, so long activities can never finish
Activity lease defaults to 1 minute and there is no way to extend it. If an activity reliably takes longer than its lease
(LLM calls, agent tools, file processing), the sequence is: A starts; lease expires; B re-claims and starts; A finishes
and is rejected as stale; C re-claims; B is rejected; and so on forever. That is a livelock that violates I1 (no lost
work), and the side effect runs concurrently and repeatedly (key is the same, but not every external system honours it).
Fix:
- `IKairosStore.HeartbeatActivityTaskAsync(task, now, extendBy)`: extends `lease_expires_at` only if `leased` and
  `lease_token` match; returns `StaleLease` otherwise.
- `ActivityContext.HeartbeatAsync()` plus an automatic heartbeat in `WorkerRuntime` every lease/3 while the activity runs.
- When a heartbeat returns `StaleLease`, cancel the activity's token so the losing attempt stops early.
- Optional per-activity `StartToCloseTimeout` and `HeartbeatTimeout` in the schedule, distinct from the lease.
Tests: simulator scenario where every activity takes 3x the lease; must complete (I1) with exactly one recorded effect (I3).

### L2 High: lease expiry is not counted as an attempt and has no backoff, so poison tasks loop forever
Re-claiming an expired lease increments the token but not `attempt` and applies no delay. A task that crashes its worker
(out of memory, process kill, infinite loop) is re-claimed immediately and indefinitely, bypassing
`RetryPolicy.MaximumAttempts`. The same holds for workflow tasks.
Fix:
- On re-claim of an expired lease, increment `attempt` (or a separate `lease_expirations` counter) in the same UPDATE.
- When the count reaches the retry policy's maximum, record a terminal `ActivityFailed` ("LeaseExpired") instead of handing
  the task out again; for workflow tasks, stop offering it and surface it as a stuck run (metric + dashboard), never drop it.
- Apply backoff to expired re-claims: the re-claim sets `visible_at = now + backoff(attempt)` rather than being eligible at once.
Tests: crash-at-every-step variant where the worker always dies mid-activity; run must end in a recorded failure after
MaximumAttempts, not loop.

### L3 Medium: lease times use the worker's clock, so clock skew lets one worker steal another's live lease
`lease_expires_at = @now + lease` and the expiry check `lease_expires_at <= @now` both use the caller's clock. With several
app instances in embedded mode (common: a scaled web app), a worker whose clock runs ahead re-claims tasks that are still
legitimately leased. Fencing keeps state correct, but the activity side effect runs twice concurrently (I3 pressure) and
work is wasted.
Fix: take lease time from the database (`clock_timestamp()`) in the Postgres store. Keep the caller's `now` for history
timestamps. Add a store option so the simulator and in-memory store keep virtual time (`LeaseClock = Database | Caller`,
default Database in production). Contract test: two workers with clocks 30 s apart must not steal each other's live lease.

### L4 Medium: graceful shutdown abandons leases instead of releasing them
On cancellation the worker records nothing and lets the lease expire, so every deploy delays in-flight activities by up to
a full lease (1 minute today; longer once agent activities get long leases). That works against the
"rolling deploys with graceful drain" goal.
Fix: `ReleaseActivityTaskAsync(task, retryAt: now)` guarded by token, called on shutdown; it does not count as an attempt.
Workflow tasks already have `ReleaseWorkflowTaskAsync`; call it on shutdown too.

### L5 Medium (performance): poll predicate is not index-friendly
The poll filters on `leased`, `visible_at`, `lease_expires_at` (and `build_id`) but the index is `(tenant, namespace, ord)`.
With a backlog of leased or future-dated tasks every poll walks past them. `NextWakeupAsync` already computes
`CASE WHEN leased THEN lease_expires_at ELSE visible_at END`.
Fix: store that as one column `available_at` (set on claim to the lease expiry, on release/retry to the retry time) and
index `(tenant_id, namespace_id, available_at, ord)`; poll with `available_at <= now`. Simplifies L2's backoff too.
Benchmark: poll latency with 100k leased + 100k future tasks in one namespace, before and after.

### L6 Low now, Medium at M7: lease length is chosen by the caller with no bounds
Any worker can request an arbitrarily long lease and hold a run hostage. Harmless in embedded mode (trusted code), not in
the standalone server with customer-hosted workers.
Fix: clamp to configured min/max in the store (and per namespace in the server).

### L7 Low: completion outcomes are discarded by WorkerRuntime
`CompleteWorkflowTaskAsync` / `CompleteActivityTaskAsync` results are ignored. `StaleLease` and `SequenceConflict` should be
counted (metric) and reported through `OnFault` so lease problems (L1, L3) are visible in production.

## Suggested order
L1 and L2 before Milestone 4 (agents depend on long activities), L3 and L4 in Milestone 2, L5 with the group-commit
benchmark, L6 and L7 by Milestone 7. Add L1/L2/L3 scenarios to the simulator and the TLA+ model (fencing + renewal).

## Follow-up review of commit 53c4399 (24 Oct 2026)

L1 to L4 meet the review's acceptance criteria. The tests are good: they include negative controls (no heartbeats, caller
clock) that prove each scenario would fail without its fix, and scheduling writes (`visible_at`) also use the database
clock, which closes a gap the original review did not name. The TLA+ full model passes. New findings:

### F1 Medium-High: parked workflow tasks are silent and have no way out
After 10 expiries a workflow task is parked (`stuck`, `visible_at = infinity`). Nothing logs it, no metric exposes it, the
hosting layer never reads `StoreStats.StuckWorkflowTasks`, and there is no API to resume or fail the run. A parked run is
therefore a silent stall, which is what I1 forbids ("nothing silently stalls").
Fix:
- Hosting: log a warning per newly parked run (run id, workflow type, build, attempt count) and publish a
  `kairos.workflow_tasks.stuck` gauge; include it in the health check (degraded when > 0).
- Store API: `ResumeWorkflowTaskAsync(run)` (unpark, reset attempt, visible now) and `FailRunAsync(run, reason)` (append
  WorkflowFailed, close, clear tasks/timers), both audited.
- Non-determinism releases (`countAttempt: true`) never park, which is right (retry until a fixed build is deployed), but
  they need the same log and metric so a bad deploy is visible.
Tests: park, observe log/metric, resume, run completes; park, fail, run closed with no leftover work (I9).

### F2 Medium: maintenance transactions lock many runs in different orders
`FireDueTimersAsync` locks up to 1,000 runs in one transaction in `due_at` order; `ReapExpiredLeasesAsync` locks up to 200
runs in activity `ord` order. Every worker runs both on every tick. Different lock orders across concurrent maintenance
transactions can deadlock; `Retry` re-runs the whole transaction after 5–15 ms, and while these long transactions hold run
locks, workflow and activity completions for those runs wait.
Fix: in maintenance paths take run locks with `FOR UPDATE SKIP LOCKED` (a busy run is simply handled next tick), order by
`run_id`, and commit in batches of about 50. Competing reapers then split the work instead of queueing behind each other.
Tests: Postgres test with 8 workers ticking concurrently over 1,000 expired leases and 1,000 due timers: exactly one
`LeaseExpired` record per expiry, one `TimerFired` per timer, no exhausted deadlock retries, completion p99 measured.

### F3 Low-Medium: timers still use the caller's clock
The status table notes timers fire on the caller's `now`. With the default database lease clock this is the last place
skew leaks in: a fast-clock worker fires timers early by its skew. Fix: compute `due_at` as `@clock + duration` when the
timer is stored and fire with `due_at <= @clock` in Database mode. Extend `ClockSkewTests` with a timer case and a control.

### F4 Low: activities that ignore their cancellation token keep running after losing the lease
Cancellation on lease loss only helps if the activity passes the token to its I/O. Document it in the activity
authoring guide, add an analyzer warning for activity methods that do not use their `CancellationToken`, and log
(with metric) every stale completion so the pattern is visible.

### F5 Model: extend the TLA+ spec with the reaper
Model `ReapExpiredLeasesAsync` (expiry recorded as a failed attempt, terminal at a maximum, workflow-task parking), then
remove the `MaxCrashes` bound and prove that every run still closes or ends in a recorded failure or an operator-visible
parked state.

### Suggested order
F1 and F2 before closing Milestone 2; F3 with them (small); F4 in Milestone 4 with the agent tooling; F5 in the
Milestone 3 model pass.
