# Review: Kairos.Agents (commits a86cf46, bdbccaf, 9c03130)

Scope: approvals, tool policy, tool credentials. Checked against SECURITY-ARCHITECTURE.md section 11 (agents never hold a
user's password; scoped short-lived credentials; read-only by default; writes need a policy or an approval) and the
encryption review (approval replay).

## What is solid
- `BaselineToolPolicy`: side-effecting tools need approval unless the owner explicitly allows them; a denial cannot be
  overridden by an approval; the decision is recorded with the step so policy changes never disturb runs in flight.
- Approvals: per-request ids, approver lists and roles, self-approval forbidden by default, timeouts; decisions deduplicated
  by a signal id that includes approval id, subject and outcome; the signal is bound into the payload encryption context,
  so a decision cannot be moved to another run or request.
- Tool credentials: per run and tool, scoped, expiring, HMAC-verified in constant time, never printed (`token=***`).
- Sagas with a TLA+ rollback model and three mutations; crash-at-every-step tests for agents.

## Findings

### A1 High (before MCP or the standalone server; Medium in embedded mode): approver identity is asserted, not verified
`AgentClient.ApproveAsync` takes an `ApproverIdentity` (subject, roles, evidence) from its caller and sends it as an
ordinary signal named `kairos.approval.<id>`. The workflow checks the subject and roles against the request, but nothing
proves the caller is that person or holds those roles. Anyone who can send a signal to the run (the Operator role, any code
holding a client, a future MCP `signal_run` tool) can approve as any subject with any role, which defeats approver lists and
the self-approval ban. Sending a raw signal with that name and a crafted payload does the same without `AgentClient`.
In embedded mode the host application is the trust boundary, so today this is a documentation gap; with MCP (Milestone 5) and
the standalone server (Milestone 7) it becomes an authorization bypass.
Fix:
1. Reserve the `kairos.approval.` signal prefix: the generic SignalRun path rejects it; add `Operation.DecideApproval` to
   `AccessPolicy` with its own role grant.
2. Make the approver verifiable: `IApproverVerifier` checks evidence the decision carries (an OIDC ID token or a signed
   approval token bound to run, approval id, outcome, subject and expiry). The workflow records the verification result as a
   step and refuses unverified decisions when the requirement names approvers or roles.
3. In the standalone server, the server stamps the authenticated caller's subject and roles onto the decision; caller-supplied
   identity fields are ignored.
4. Document clearly for embedded mode: the host must pass only an identity it authenticated.
Tests: a raw signal named `kairos.approval.*` is refused; a decision whose evidence names a different subject, run, approval
or outcome is refused; self-approval through a forged subject is refused.

### A2 Medium: tool credentials are symmetric and not audience-bound
`HmacToolCredentialIssuer` signs with a shared key, so every tool service that verifies tokens can also mint them, and
`Verify` checks the scope but not which tool the token was issued for: a token issued for tool A is accepted by tool B if
the scope string matches.
Fix: add an asymmetric issuer (Ed25519 or ECDSA P-256) as the recommended default, so tools hold only a public key; keep HMAC
for single-service setups and say so. `Verify` takes the expected tool (audience) and rejects others.
Tests: a token for tool A is refused by tool B; an asymmetric verifier cannot mint.

### A3 Low: document credential lifetimes and the jti
State default and maximum lifetimes in the docs and enforce a maximum in the issuer. The `jti` exists but is not checked;
fine for short lifetimes, note it, and add an optional one-time-use check for high-risk scopes.

## Order
A1 steps 1 and 4 now (small); A1 steps 2 and 3 and A2 before Milestone 5 (MCP), since MCP exposes approvals to outside agents.

## Status (after the fixes)

- **A1 done** except step 3. Reserved `kairos.approval.` prefix (`KairosClient.SignalAsync` throws, the inbound processor drops bus messages that use it, `DecideApprovalAsync` is the only sender); `Operation.DecideApproval` with a new `Role.Approver` (not granted to Operator or Admin; matrix test updated); `IApproverVerifier` plus `HmacApprovalTokens` (bound to run, approval, answer, subject, roles, expiry); the verification is a recorded step (`kairos.agent.approval.verify`), the verified subject and roles replace the claimed ones, and without a verifier a request that names approvers or roles refuses every decision. Docs state the embedded-mode trust boundary. Tests: `ApproverVerificationTests` (reserved name, forged store write, wrong subject/approval/run/outcome, expiry, forged roles, forged self-approval, no verifier, verifier down, replay does not re-verify, bus message dropped).
- **A1 step 3 open (Milestone 7):** the standalone server must stamp the authenticated caller's subject and roles. The hooks it needs exist (`DecideApprovalAsync`, `Operation.DecideApproval`, `Role.Approver`).
- **A2 done.** `EcdsaToolCredentialIssuer` / `EcdsaToolCredentialVerifier` (public key only, cannot mint), `IToolCredentialVerifier`, `Verify` takes the expected tool, token kinds have distinct prefixes. HMAC kept and documented for single-service setups. `Verify` signature changed (breaking, pre-release).
- **A3 done.** 15-minute maximum enforced in both issuers and documented; every token has a unique id exposed as `TokenId`; `OneTimeUseGuard` for high-risk scopes (in memory, per process).
- Side effect worth knowing: an approval whose token expired before the decision reached the run stays open, and the approver decides again (the signal id includes a digest of the evidence, so the second decision is a new delivery).
- Open: a shared (non-in-memory) one-time-use store for scaled-out tool services.
